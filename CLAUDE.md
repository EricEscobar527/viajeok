# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**ViajeOK** (`AppInfo.name`, Android/iOS labels, accessibility service label, ARB texts) is an Android-first Flutter app. Dart package `viajeok`; Android namespace/applicationId `cloud.doublee.viajeok` (permanent once on Play; Kotlin under `android/app/src/*/…/cloud/doublee/viajeok/`); method channel `viajeok/reader`. The project folder is `viajeok` too, and so are the desktop runners' binary names. It's for ride-hailing drivers, modeled on "Ruta Rentable": while DiDi Conductor or Uber Driver is open, it reads the trip offer on screen, computes $/km and $/h, and shows a popup over the ride app whose border is green (worth it) or red (not), based on the user's filters. UI text is in Spanish. Exactly two ride apps are supported, DiDi Conductor and Uber Driver, fixed in `ReaderState.packages` and the service's `packageNames`; the user decided there is no setting to change them, and inDrive/Bolt are out. The UI was redesigned to look unlike the original: lighter slate-gray palette, white accent (`AppColors.accent`), squared `kRadius` corners, solid buttons instead of gradient pills, outlined icons, borderless cards; `AppColors.green`/`red` are reserved for accept/reject meaning (the popup, the live dot), so don't use green as a general highlight. There is no bottom bar: a single home panel, with Soporte behind a header icon. The user removed Config, Billetera, the language selector, the country chip, Cámara, Premium, the header menu and the Turbo filter; don't add them back unless asked.

Current state: works end to end on a real phone with DiDi Conductor; Uber Driver is wired in but not yet verified with a real offer (its card format and whether it needs OCR are unknown) via "Lectura de pantalla" (AccessibilityService + screenshot OCR). The user dropped "Compartir pantalla" (MediaProjection) for now; it may be needed later only if Google Play rejects the accessibility-service approach, so don't re-add it unprompted.

## Architecture

- **Startup flow** (`lib/main.dart`): `main()` loads `AppPrefs` before `runApp`, then `_Start`, which shows `OnboardingScreen` until `onboarding_done` is set, then `HomeShell` on every later launch.
- **No splash**: the user asked to remove the animated "ViajeOK" intro, so the app opens straight on onboarding/home. Only Android's native launch color shows while Flutter starts: `AppColors.background` (`#1F2329`) must match `android/app/src/main/res/drawable*/launch_background.xml` (and `TripOverlay.kt`'s BACKGROUND) or a flash appears.
- **Onboarding** (`lib/onboarding/`): one welcome screen with an "Empezar" button; the user asked for a minimal install. No permission is asked there: the only one needed (the accessibility service) is requested by `PanelScreen` the first time ▶ "Iniciar análisis" is pressed. Before sending the user to Android's settings, `PanelScreen` always shows `AccessibilityDisclosureScreen` (`lib/home/accessibility_disclosure_screen.dart`), Google Play's required prominent disclosure. Settings opens only on "Acepto". Its section texts (`disclosure*` keys in the ARB files) are written by the app owner and are still `[PENDIENTE]`: they must be filled in before uploading to Play. Don't draft those texts; leave them to the owner. The overlay permission (SYSTEM_ALERT_WINDOW) was removed: the popup is a TYPE_ACCESSIBILITY_OVERLAY and doesn't need it.
- **Trip reading** (`android/app/src/main/kotlin/.../reader/`): `TripReaderService` is an AccessibilityService limited to DiDi Conductor (`com.didiglobal.driver`) and Uber Driver (`com.ubercab.driver`) in `res/xml/trip_reader_service.xml`. While analysis runs and a ride app is in front, it re-reads the screen every `POLL_MS` (DiDi fires no accessibility events while an offer is shown, so events alone aren't enough) plus on events. Each read first tries the apps' accessibility text; if `TripParser` finds no offer there, `ScreenOcr` takes an accessibility screenshot (API 30+, `canTakeScreenshot`, ~1/s limit), crops the top 20%, halves it, runs on-device ML Kit OCR and drops lines overlapping our own popup, then feeds the lines to the same parser. Verified on a real phone: DiDi Conductor's offer card is Flutter with no accessibility text and its view tree gives no reliable "offer showing" signal (the `flutter_deal_gesture_container` id is present while idle and disappears during offers), so OCR is what actually reads DiDi. `TripParser` extracts the fare and legs. The formats it supports are documented in its KDoc and covered by `TripParserTest` (DiDi), `RealOcrTest` (exact on-device OCR output, misreads included) and `UberParserTest` (Uber rides with `MXN` prefixes and "A … / Viaje: …" legs; Uber deliveries with a single "Total:" leg, where `hasPickup=false` and the Pickup máx. filter is skipped). Before parsing, `ocrDigits` fixes OCR digit look-alikes inside number tokens ("lh 44 min" → 1h, "O9 min" → 09) without touching words. Fare preference: the "Aceptar $X" line, else the first amount that isn't a rate ("/km"), an included bonus ("+$8.00 incluido"), a tip note or a base fare. The popup hides `HIDE_AFTER_GONE_MS` (2.5 s) after the offer was last seen; later "gone" reads must not reschedule that hide. Offers are deduplicated by their legs, and a later OCR that sees the same legs without a fare (our popup covering a tall card) keeps the popup instead of flickering; `TripEvaluator` applies the filters (pickup counts toward $/km and $/h; accept only if every enabled filter passes); `TripOverlay` draws a non-touchable TYPE_ACCESSIBILITY_OVERLAY card with a green/red border, placed per app (`topFor`): on DiDi at `DIDI_TOP` (12% of screen height), below DiDi's "Rechazo permitido" button and above its card; on Uber right under the status bar, because tall UberX cards start near the top and the fare must stay visible. Debug builds log every read (`adb logcat -s ViajeOK:D`) and keep the last 40 OCR inputs in the app's `cache/ocr/`. Unit tests: `android/app/src/test/`. To check a saved offer screenshot on a real phone without a live offer, debug builds include `DebugOfferActivity` (`src/debug/`). Push the image into the app's files dir, launch the activity with `--es image <name>` (usage in its KDoc), and it runs the image through OCR → parser → filters → popup and logs the result.
- **Dart ↔ service**: `lib/platform/trip_reader.dart` ↔ `MainActivity.kt` over `viajeok/reader`. The service can't read Flutter's prefs, so Dart pushes the filters (`TripReader.pushConfig`); add new Android-only calls to this channel instead of pulling in a plugin. It pushes them on launch and after every change; `ReaderState.kt` stores them (its package set is the fixed DiDi + Uber constant) plus the `running` flag. The user removed the offer counters (Ofertas/Convienen/No convienen): nothing about past offers is stored. Filter names (`FilterKind.name`) must stay identical in Dart and Kotlin. `lib/data/trip_filters.dart` only holds filter settings/slider ranges.
- **Turning the service off**: banking apps (verified with Nu) refuse to open while any accessibility service is on, and "Detener análisis" only clears the `running` flag. So while the service is enabled, `PanelScreen` shows a "Lectura de pantalla activa → Desactivar" card. After a confirm dialog, `TripReader.disableService()` → `MainActivity` `disableService` stops the analysis and calls `TripReaderService.turnOff()` (`disableSelf()`, API 24+), so users never have to uninstall. If the service isn't connected, Android's accessibility settings are opened instead. Re-enabling goes through the normal ▶ flow.
- **Support** (`lib/support/support_screen.dart`, opened from the header's (?) icon): a form with three problem option cards (1 wrong calculations, 2 alert not shown, 3 other). Options 1–2 ask phone model (text) and screenshots (`image_picker`, up to 5); option 3 asks a description; all three ask for a validated email. After sending, a dialog says the average response time is 12 hours. The backend is the user's own API (`POST <base>/support/tickets`, multipart, `Authorization: Bearer <token>`, 201 → `{id, folio}`; 400 field errors, 401 bad token, 429 rate limit). `lib/data/support_api.dart` holds `SupportTicket.toFormFields()` (field names: `issue`, `email`, `phone_model`, `message`, `device_time`, app/Android/device fields, files as repeated `images`), `HttpSupportApi`, and the failure mapping the form turns into messages. The success dialog shows the folio. Production API: `https://admin.doublee.cloud/api` (the path needs `/api`). Base URL and token come from `--dart-define-from-file=env/dev.json`, or `env/prod.json` for release builds, (`SUPPORT_API_BASE_URL`, `SUPPORT_API_TOKEN`; git-ignored, template in `env/example.json`, used by `.vscode/launch.json`). Never hardcode them. Without them, `UnconfiguredSupportApi` makes every send fail (debug builds log why). It must never fake success: a run without the config once made a user believe a report was sent. `.vscode/settings.json` (`dart.flutterRunAdditionalArgs`) applies the env file to every VS Code run, including the Run/Debug CodeLens. Plain http to the dev PC works only in debug builds (`usesCleartextTraffic` in `src/debug/AndroidManifest.xml`); production must be https. Backend changes requested from the user: issue codes `wrong_calculation`/`alert_not_shown`, `message` optional except for `other`, new `phone_model` field. Until those land, options 1–2 get a 400. Tests inject a fake API (`test/support_test.dart`).
- **Persistence** (`lib/data/app_prefs.dart`): a thin wrapper over `shared_preferences`; filters are stored as `filter_<kind>_on` / `filter_<kind>_value`. Screens read prefs directly and write on change; there is no state-management package.
- **Localization**: all user-facing text lives in `lib/l10n/app_es.arb` (template) and `app_en.arb`; `flutter gen-l10n` (also run automatically on build) regenerates `lib/l10n/app_localizations*.dart`. Never hardcode UI strings: add a key to both ARB files and use `AppLocalizations.of(context)`. The app launches in Mexico only, so `MyApp` pins `locale: Locale('es')`; the user removed the language selector and the country/flag chip. English is kept in the ARB files so it can be re-enabled later. The brand name `AppInfo.name` is intentionally untranslated.
- **App icon**: source art in `assets/branding/ViajeOK_icon_1024.png` (and `_512` for the Play listing), not bundled in the app. `dart run flutter_launcher_icons` (config at the end of `pubspec.yaml`) regenerates Android `launcher_icon` mipmaps, the adaptive icon (background `#1F2328` + the art inset 16%, so the full-width wordmark stays inside the mask's safe zone) and iOS icons. After regenerating, delete any leftover `mipmap-*/ic_launcher.png`. Phones may show a cached old icon until the launcher or Settings restarts.
- **UI**: colors live in `AppColors` (`lib/theme/app_theme.dart`); reusable pieces (`PrimaryButton`, `AppCard`, `IconTile`, `StatusBanner`, `FeatureRow`) are in `lib/widgets/common.dart`. The app name is in `lib/app_info.dart`.

## Testing notes

- Widget tests must call `SharedPreferences.setMockInitialValues(...)` and pass `await AppPrefs.load()` to `MyApp`, then `pumpAndSettle()` to get past the splash.
- Tab content is in `ListView`s, so off-screen widgets aren't built in the 800×600 test viewport; use `scrollUntilVisible` before asserting on them.
